## Bug — false-success data loss in Notes

Swept the client-side silent-write-failure class across all 81 writing
`components/modules/*.tsx` (browser `supabase.from().update/delete/insert()`
that drops the PostgREST `{ error }` before an unconditional success/optimistic
UI). Almost all route through `useAction`/server actions (throw → toasted) or
already capture `{ error }`. Two genuine bare-await bugs remained in
**`notes-module.tsx`**, a module under no active claim:

- **`duplicate()`** ran `.insert(...)` then unconditionally toasted
  **"Note duplicated"** — a failed copy (RLS denial / offline / constraint)
  reported success and silently lost the note. (Contrast the sibling
  `deleteNote`, which guards correctly.)
- **`togglePin()`** ran `.update({ is_pinned })` and optimistically mutated the
  open-note viewer state, so a failed write left the UI showing a pin state the
  DB never stored.

**Fix:** both now `const { error } = await …; if (error) return toastError(describeDbError(error));`
before any success toast / optimistic `setViewing`, matching the module's own
`deleteNote`/save pattern. No new deps, no signature changes.

**Guard test:** `tests/notes-module-write-boundary.test.ts` (4 assertions) —
each write destructures + guards `{ error }`; success/optimistic-state only after
the guard. Mirrors `recipes-module-write-boundary`.
