# Internationalisation

Bubaly ships eleven locales. A visitor's language is detected from where they
are, overridable from a control on every page, and remembered for a year.

| Layer | Files |
| --- | --- |
| Locale catalogue + country/language mapping | `lib/i18n/locales.ts` |
| Precedence rules (pure, unit-tested) | `lib/i18n/resolve.ts` |
| Catalogue loading + `translate()` | `lib/i18n/messages.ts`, `lib/i18n/messages/*.json` |
| Server-side resolution | `lib/i18n/server.ts` (`getLocaleContext`, `getTranslations`) |
| Client context + hooks | `components/i18n/locale-provider.tsx` (`useTranslations`, `useLocale`) |
| The picker | `components/i18n/language-picker.tsx` |
| Persisting a choice | `lib/i18n/actions.ts` (`setLocale`) |
| Scanner / CI gate | `scripts/i18n-scan.mjs`, `scripts/i18n-gate.mjs` |
| Tests | `tests/i18n-locale-resolution.test.ts` |

## How a locale is chosen

`resolveLocale()` takes the first of:

1. **The `bubaly-locale` cookie** — an explicit choice. Always wins: someone who
   has told us what they read must keep reading it while travelling.
2. **Edge geo** (`x-vercel-ip-country`) — the "identify the location you are in"
   default.
3. **`Accept-Language`** — weaker than geo for a family product. A US-configured
   laptop in Mexico City is likelier a Spanish-speaking household.
4. **`en-US`.**

An unrecognised cookie is ignored rather than trusted, so a stale or hand-edited
value degrades to detection instead of breaking the render.

Resolution happens in the **root layout, on the server**, so the first paint is
already correct. Doing it in the browser would flash English on every load for
everyone outside the US.

### Ambiguous countries

Some countries are claimed by more than one locale — Canada carries `fr-CA`'s
region code, the United States carries `es-US`'s. `COUNTRY_LOCALE` is consulted
**before** the region scan so array order can never decide these. Canada defaults
to English (roughly three-quarters anglophone); francophone visitors are caught
by `Accept-Language` and can pick `fr-CA` from the menu.

## Adding a string

1. Add the key to `lib/i18n/messages/en-US.json`.
2. Translate it in the six base catalogues.
3. Render it with `t('your.key')` — `useTranslations()` in a client component,
   `await getTranslations()` in a server component.

Keys are flat and dotted (`shell.signOut`). A key missing from a translation
falls back to English, so a lagging catalogue renders an untranslated product
rather than a broken one.

See `lib/i18n/messages/README.md` for the base-catalogue/regional-overlay split.

## The scanner

`npm run i18n:scan` lists user-facing English still hardcoded in `app/` and
`components/`. It reports only strings that look like prose, and skips the many
string-shaped things in React that are not copy — class names, ids, URLs, enum
values, expression fragments. A scanner that cries wolf gets muted.

`npm run i18n:gate` fails if a surface listed in `GATED_SURFACES` has regained a
hardcoded string. **Adding a surface there is a promise** — only add one that
scans clean. Translating a surface is easy to undo by accident: someone adds a
button, types the label inline, and every non-English visitor silently gets
English on a page that was clean yesterday. Nothing else in the build notices.

## Current coverage

Honest numbers, from `npm run i18n:scan`:

| | |
| --- | --- |
| Hardcoded strings remaining in `app/` + `components/` | **7,402** across 582 files |
| Surfaces gated as translated | app shell, marketing header, the picker |

Roughly 2,400 more strings live in `lib/` constants — module and navigation
labels defined as data — and are not counted above. Seeded database content
(blog posts, marketing pages) is a separate problem: it is rows, not source, and
needs a per-locale column or a translation table rather than a catalogue.

**This is a real multi-week migration, not a switch.** The foundation, the
control, the detection and the guardrails are done and shippable; the long tail
of copy is the remaining work. The scanner is how progress gets measured, and
the gate is how finished surfaces stay finished.

### Translation review

The shipped catalogues were written directly rather than by a translation
vendor. They are short, high-frequency UI strings and are accurate, but they
have **not had native-speaker review**. Before marketing a locale as supported,
have a native speaker pass over its catalogue — particularly `de-DE` compound
nouns and the `pt-PT` / `es-ES` formality register, where a plausible-looking
string can still read as machine output.

## Known gap: static rendering

Reading the locale cookie in the root layout opts the whole tree into dynamic
rendering. Most of this app was already dynamic (247 of 379 routes force it),
but a handful of marketing routes were statically prerendered and no longer are.

The fix, when marketing SEO warrants it, is locale-segmented URLs
(`/es-MX/pricing`) rather than a cookie: that restores static generation per
locale and gives search engines distinct URLs to index with `hreflang`. It is a
large refactor across 379 routes and was deliberately not attempted alongside
the foundation.
