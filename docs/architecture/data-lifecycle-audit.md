**Current implementation evidence and gaps**

1. **Member deactivation is present; complete revocation is not established.** The removal handler in `components/modules/family-module.tsx:446` updates `family_members.is_active` to false and refreshes the member list. It checks the returned error but does not require an affected-row result before announcing success. It does not itself perform responsibility reassignment, departure export, ownership transfer, or a durable audit write. The separate administrative UI invokes `adminRemoveMemberAction` at `components/admin/member-row-actions.tsx:21`; its backend body was unavailable in the truncated response, so its semantics are unassessed. The member listing in `app/(app)/family/members/page.tsx:20` filters active members, which demonstrates presentation filtering rather than access revocation.

   The inspected `is_family_member`, `can_manage_family`, and `is_family_admin` definitions check active membership in `supabase/migrations/0003_functions_triggers.sql:5`. Migration `supabase/migrations/0211_family_members_update_rls.sql:11` replaces the earlier self-update exception with manager authorization for both the existing and resulting row. These are useful mechanisms, conditional on the effective policy chain. The removal handler alone does not prove that every query, service-role action, subscription, worker, or media delivery path consults them after removal.

2. **The sampled profile policy leaves a concrete revocation concern.** In `supabase/migrations/0118_rls_drift_repair.sql:35`, profile visibility joins the requester's membership to another person's membership without requiring either membership to be active. The same shape appears at `supabase/migrations/0004_rls.sql:42`. If this policy remains effective, retaining an inactive membership can still satisfy the shared-family branch and expose another person's profile after removal. Migration 0211 changes membership UPDATE authorization, not this profile SELECT predicate. In addition, the sampled `family_role` function at `supabase/migrations/0003_functions_triggers.sql:13` lacks an activity filter; callers that rely on it alone need separate assessment. Later replacements and actual grants were not exhaustively inspected. These are source-level concerns, not claims of reproduced production exposure.

3. **Media access has a boundary beyond membership rows.** `supabase/migrations/0216_family_media_bucket.sql:22` declares the `family-media` bucket public and intentionally preserves public-URL delivery. Its comments explain that changing visibility requires migration of stored references. Its family-scoped SELECT policy does not, by the migration's own design, govern public-URL delivery. Consequently, this migration cannot support a claim that member deactivation revokes previously obtained media URLs. The private documents bucket is separately declared in `supabase/migrations/0007_home_asset_warranties.sql:18`; `lib/storage/documents.ts:38` issues signed URLs with a default lifetime of 120 seconds. The behavior of an already issued URL after revocation was not exercised. Later storage changes, deployed bucket settings, CDN behavior, and link revocation are unassessed. Already downloaded copies also require a clearly stated product boundary.

4. **Account closure is deliberately reversible retention.** `app/(app)/account/actions.ts:19` calls `requireUserContext`, checks `isAdmin`, and uses a service client to set the active family's `closed_at`; reopening clears the field. The definition of the context resolver could not be assessed from the truncated output, so freshness of its authorization is not certified. The confirmation in `components/app/close-account-card.tsx:17` and the reopen interface in `components/app/account-closed-gate.tsx:19` explicitly describe preserved data. `supabase/migrations/0164_family_trial_and_close.sql:18` adds closure and trial columns and indexes. None of those operations implements a deletion job, token revocation, storage cleanup, retention expiry, or a worker stop barrier. Rendering and enforcement of the gate throughout the app were not traced.

   Separately, `supabase/migrations/0118_rls_drift_repair.sql:61` and `supabase/migrations/0004_rls.sql:67` define family DELETE authorization using the family-admin predicate. They do not encode a confirmation receipt or durable cleanup workflow. If effective grants expose this operation, it is a potential path around a future deletion workflow. Effective grants and later policies must be established before treating the UI as the only deletion boundary.

5. **Existing exports are administrative CSV serializers.** `components/admin/users-toolbar.tsx:15` serializes supplied user-report rows and downloads a CSV. `components/admin/reports-toolbar.tsx:6` does the same for supplied user-activity, subscription, and content-report rows. They quote fields and escape embedded quotes. They do not implement a household export scope, per-record privacy selection, document originals/versions, an export manifest, or a fresh authorization decision at download time. Their upstream loaders and administrative authorization were not assessed; their presence is not evidence of an unauthorized export either. CSV escaping alone does not document the handling of spreadsheet formula-looking values.

   A requester-authorized household export was not established in the inspected paths. This is an evidence gap, not a repository-wide claim that no exporter exists. An acceptance decision needs a demonstrated section-110 scope and explicit omissions, rather than relabeling these reports as household portability.

6. **Rows, objects, and retained audit history need a coordinated policy.** The selected `documents` definition at `supabase/migrations/0002_tables.sql:341` stores a storage path while cascading the document row on family deletion. The selected `audit_logs` definition at line 454 also cascades on family deletion. The warranty migration adds another document-row cascade at `supabase/migrations/0007_home_asset_warranties.sql:10`. Those foreign keys do not themselves demonstrate removal of corresponding object bytes or a minimized retained-audit exception.

   `lib/storage/documents.ts:48` can remove a named object, but is not a tenant cleanup coordinator. The administrative document UI at `components/admin/document-row-actions.tsx:24` sends a document ID and storage path to its backend after confirmation. The unavailable backend body prevents conclusions about path validation, deletion ordering, or recovery. In particular, accepting a path as a UI argument does not prove that the backend trusts it. The separate row-delete example in `components/modules/security-module.tsx:81` likewise demonstrates a domain operation, not complete tenant deletion.

   `lib/server/audit.ts:4` explicitly provides best-effort logging. It catches thrown failures but does not inspect the database insert's returned error object. It cannot serve by itself as a durable completion receipt. No inspected coordinator establishes cleanup of semantic indexes, embeddings, extraction caches, AI traces, or other derived artifacts. Retention and any required audit exceptions must be explicit before executing destructive work.

7. **Provider disconnect attempts exist, but completion can be ambiguous.** Both `app/api/sync/[provider]/disconnect/route.ts:11` and `app/api/sync/google/disconnect/route.ts:9` scope an account lookup by active family, requester, and provider. They request the refresh token, attempt revocation, delete the account row, and insert a disconnect audit record. The generic route suppresses token-read and provider-revocation failures. Both routes omit checks of the lookup, delete, and audit error objects and redirect with `disconnected=1`. An empty or errored lookup can therefore reach the same redirect as a completed operation. The Google route does not locally catch a thrown revocation failure; the actual adapter's behavior was not inspected.

   `lib/sync/accounts.ts:32` supports account identity including `external_id`, whereas the disconnect lookups use `maybeSingle()` without an individual account ID or external ID. Multiple accounts for the same requester/provider/family require an explicit selection contract. Comments in the routes describe cascades and retention of imported calendars/events; those cascade definitions and actual imported-data outcomes were not assessed. The code provides no requester choice here or durable record of unfinished provider revocation. `getValidAccessToken` at `lib/sync/accounts.ts:108` does not itself check a membership or deletion barrier. Caller and worker enforcement remain unassessed.

**First safe vertical slice**

The recommended first implementation slice is the existing member-removal flow through the next protected profile read, proved with local synthetic identities. It addresses a concrete sampled policy concern, retains membership history and existing IDs, and requires no export or destructive tenant cleanup. It is a proposal only; this audit changes no policy or account.

1. Establish the effective profile SELECT policy in an isolated local migration fixture before changing it. If a later migration already closes the inactive-membership branch, record that evidence and exercise the existing behavior rather than adding a duplicate repair.
2. If the concern remains, add a narrowly targeted migration for the profile-visibility policy. Preserve allowed self-profile reads. Require appropriate active membership on the requester and target relationship for shared-household visibility. Resolve any intended access to departed private profiles explicitly, rather than preserving it accidentally through an inactive row.
3. Exercise the real removal transition with synthetic data: active authorized reads succeed before removal; the membership row and relationships remain present with `is_active=false`; the same session's next query cannot retrieve another household member's profile. Verify that permitted self-profile access and the user's unrelated active household still work. Include a denied remover, a stale target, and concurrent departure/read ordering.
4. Capture the effective-policy definition, actor/outcome matrix, membership and relationship counts, and recovery procedure. Restore authorization only through an explicit authorized reactivation; a rollback must not silently re-open departed-member access. Keep older schema readers/writers compatible as required by section 93.
5. Accept only this demonstrated database-read boundary. Public media, outstanding signed URLs, other service and worker paths, departure exports, responsibility reassignment, and durable deletion remain separate open proof obligations. This slice must not be advertised as complete immediate revocation or household deletion.
