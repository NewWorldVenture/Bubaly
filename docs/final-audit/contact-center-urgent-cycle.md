## Reproduced failures

The original eight execution cases ran the real middleware, signed SMS/voicemail handlers, inbox capture and Twilio fetch helper with synthetic storage/network. Both channels acknowledged a confirmed 429, then skipped escalation on the next callback because the inbox already existed. A simulated crash immediately after the real inbox commit lost both alerts. A returned notification insert error was silently ignored. An accepted-but-lost provider response had no durable receipt or uncertainty marker. All eight original defect-characterization assertions passed before repair; they are now recovery assertions in `tests/contact-center-urgent-durability-repro.test.ts`.

Security review also found that `recordInboundMessage` used `upsert(onConflict: 'channel,provider_ref')`, while migration0214 supplies only `UNIQUE(channel,provider_ref) WHERE provider_ref IS NOT NULL`. A plain PostgREST conflict target cannot infer that partial index. The new capture path uses plain insert; only23505 triggers a required exact duplicate read. The read verifies family, channel, provider ref, direction and complete row count. A different constraint or foreign family cannot be accepted as a delivery duplicate. No SQL was changed or applied. Actual installed-SDK tests verify the emitted HTTP contract; PostgreSQL itself was not executed.

## Implemented behavior

- All three inbound handlers persist a deterministic service-owned receipt with bounded original recovery inputs **before** inbox capture or acknowledgement. A crash before or after inbox insertion can be recovered by the worker without another AI call. The namespace is `contact_center.urgent_delivery:`; IDs derive from family/channel/provider identity.
- Receipts use existing `ai_tool_calls` columns, actor `system`, null requester/run/request/step/conversation/message references, versioned inputs/outputs and a canonical primary key. They are never registered as executable AI tools. Migration0250 limits their reads to family managers and their writes to the service role. The independent consumer/RLS review is in `contact-center-urgent-security-review.md`.
- The in-app alert has its own deterministic notification primary key. Insert-ignore preserves `is_read`, `sent_at`, and `pushed_at`. Notification repair proceeds independently from SMS, including when no SMS fallback is configured. Email urgency now receives the same independent in-app alert.
- A fresh family/contact-channel read precedes each new SMS claim. The saved recipient must still match current routing; the current fallback is used. A removed fallback resolves to in-app-only. Missing provider configuration stays queued without claiming an external attempt.
- Every receipt transition is fenced by the exact unique revision and state observed by that worker. The external call begins only after a durable `dispatching` claim. A concurrent repair cannot change the revision held by an in-flight send. Accepted receipt persistence failure leaves that claim held.
- The Twilio adapter makes one credentialed fixed-host POST, forbids redirects, bounds the response and carries a maximum15-second provider deadline inside a25-second attempt budget. Only HTTP201 with a valid message SID and recognized acceptance state is accepted. A SID is evidence of provider acceptance, not handset delivery. [Twilio message resource](https://www.twilio.com/docs/messaging/api/message-resource).
- Only confirmed429 rejection automatically retries, with exponential backoff and at most five claimed attempts. Twilio documents429 as not processed. Other4xx failures require correction;408,5xx, redirects, network/timeout, malformed or oversized successful responses remain unknown. Unknown or dispatching work is never reclaimed merely because time elapsed. [Twilio retry guidance](https://www.twilio.com/docs/usage/rest-api-best-practices).
- Required receipt/notification/routing storage failures return503 **after** independent planner/paperwork/attachment recovery runs. Durable pending or uncertain delivery may acknowledge intake. Urgent auto-replies use the translated saved-inbox acknowledgement and never claim that an SMS was sent. Persisted receipt errors are safe translated text, not raw provider diagnostics or untranslated keys.
- An existing inbox message with no receipt is explicitly `legacy_unknown`; it is never assumed unsent. There is no blind historical resend or backfill.

## Scheduled recovery

New `/api/cron/contact-center-urgent` requires the existing nonempty `CRON_SECRET`. The GitHub dispatcher calls it every five minutes. `vercel.json` adds a daily01:00UTC fallback compatible with the existing Hobby deployment setup. Existing route schedules, tick lookback and dispatch concurrency are unchanged.

The drain processes at most10 receipts by default (hard maximum20), stops starting work after65 seconds, and gives each attempt25 seconds plus bounded queue/cursor operations. Its route budget is110 seconds. It traverses stable `created_at,id` keys one row at a time and wraps using a validated service-only `app_settings` cursor. Held or unavailable rows cannot indefinitely hide later healthy rows in sequential bounded runs. Cursor read/write failure is visible. The cursor is progress, not a distributed lock; SMS exclusivity comes from each receipt's revision claim. The cron reports unavailable when examined work is pending, uncertain, rejected or failed.

## Remaining limits

Synthetic HTTP/storage execution does not verify live Supabase RLS/index execution, deployed provider callbacks, production credentials, scheduler enablement, Twilio acceptance or handset delivery. The fallback SMS still uses the application's configured Twilio sender. A provider acceptance followed by a lost response remains deliberately held for human verification; no safe automatic receipt lookup or operator resend interface is implemented in this cycle. A crash after the durable dispatching claim but before network send is also held rather than risking duplication.

There is no transaction spanning a channel/fallback change and a provider POST; revocation after the final checked read cannot cancel an already-started external request. Persistent poison/held rows remain observable and consume bounded scan capacity. Very large backlogs need operational throughput sizing. The five-minute GitHub scheduler must actually be enabled; the daily fallback does not promise prompt recovery.

Sender-controlled email Message-Id values still share the schema's global channel/ref uniqueness. A same-ID message addressed to two families fails closed for the second family instead of being misrouted; resolving that availability constraint requires a separate compatible identity migration/design. Byte-identical deliveries without provider IDs use the established derived identity and may collapse. AI classification still precedes capture. Ordinary concierge SMS/email auto-replies can repeat on callback replay; this cycle repairs urgent escalation only. No claim of exactly-once handset delivery or complete end-to-end Contact Center PASS is made.
