# JOB-001 — Required cron dispatch configuration and execution boundary

Date: 2026-09-12. Baseline: currentmain c7b56eff. Root recorded JOB-001 IN PROGRESS before these changes. Owned files: `scripts/cron-dispatch.mjs`, `.github/workflows/cron-dispatch.yml`, `tests/cron-dispatch-execution.test.ts`, and this record. No actual cron endpoint, provider, database, secret or repository setting was changed by verification.

## Baseline failure

A real CLI subprocess at `2026-09-12T12:05:00Z`, with `CRON_SECRET` unset and fetch replaced before entrypoint evaluation, reported three due routes and then:

```text
CRON_SECRET is not set — skipping (add it under Settings → Secrets → Actions).
```

It exited **0**, causing a successful job despite dispatching nothing. The workflow documentation explicitly described that behavior. The new CLI execution suite initially had **16 failing / 7 passing** cases, including absent configuration and credential-safe dispatch controls.

## Changes

- A real dispatch requires a nonblank `CRON_SECRET`; missing configuration produces a named configuration error and exit **1** without any fetch. A multiline secret is rejected before header construction. Messages do not print configuration values.
- Explicit `--dry-run` remains credential-free, prints the due route selection and performs no fetch.
- Manual `--route` must name one of the existing registered cron routes. Missing or invalid route arguments exit **2** rather than silently running all due routes or concatenating an arbitrary destination onto the base URL.
- `CRON_BASE_URL` remains optional with the same production default. Configured values must be HTTPS origins without embedded credentials, paths, query or fragment. HTTP is accepted only for loopback localhost, 127.0.0.1 or [::1], preserving local testing while keeping the dispatch secret off public plaintext connections. Invalid config exits **2** without echoing the value or sending credentials.
- Requests refuse automatic redirects; 3xx, non-2xx, network/stream errors and timeout become failed dispatch results and nonzero process exit. The existing 120-second request deadline and concurrent due-route dispatch remain intact.
- Response diagnostics read at most **4,096 bytes**, cancel the remaining body, collapse whitespace and print at most 200 characters. The configured secret is redacted from both response and thrown-error diagnostics.
- CLI entrypoint detection now uses Node's `pathToFileURL`, supporting the actual script path without manually constructing a file URL.
- Workflow comments and step name now state that configuration is validated and missing required credentials fail the job. The script's nonzero exit propagates through the existing shell step.

**No schedule or catch-up semantics changed.** All 22 entries in SCHEDULES, `TICK_MINUTES = 5`, the five-minute workflow schedule, repository restriction, concurrency policy and workflow timeout remain unchanged.

## Remaining scheduler scope, separate from this fix

- The dispatcher uses a fixed five-minute retrospective window ending at invocation time. It does not store the previous successful tick or a per-route cursor. A delayed/missed invocation can therefore miss a daily/hourly due minute outside that window. This is a repository scheduling reliability item requiring an explicit catch-up/idempotency design; no schedules/lookback were silently changed here.
- Live GitHub Actions configuration, actual secret equality with deployment, production URL reachability and deployed handler authentication were not exercised. The CLI now fails clearly for absent config, but these tests do not establish that production secrets/settings are configured correctly.
- The dispatcher classifies completion by transport/HTTP status. The success or partial-failure semantics inside each route's JSON response and durable work must be verified in that route's workflow; HTTP 200 alone is not proof that every background action completed.
- These tests validate orchestration boundaries with synthetic responses, not actual provider delivery, database writes, cron idempotency, or worker lease recovery.

The falsely green missing-secret dispatch defect is fixed and locally retested. Production readiness remains **NO** pending the remaining scheduler and application audit workflows.

## 2026-10-03 — Catch-up window (the first "remaining scheduler scope" item)

Baseline: main `1421c745`. Owned files: `scripts/cron-dispatch.mjs`, `.github/workflows/cron-dispatch.yml`, `tests/cron-dispatch.test.ts`, `tests/cron-dispatch-execution.test.ts`, `tests/a-late-tick-catches-up.test.ts` (renamed with `git mv` from `tests/a-late-tick-drops-a-cron.test.ts`, so history follows), and this record. `SCHEDULES` is byte-identical, `TICK_MINUTES` is still 5, the workflow's cron string, sparse checkout, concurrency group, timeout and repository guard are unchanged. No endpoint, secret or repository setting was touched; the Actions API call was exercised only by a local simulation of the step's shell with a fake `gh`.

### The defect

`dueRoutes` looked back a fixed `TICK_MINUTES` ending at the invocation time and stored nothing about the previous tick. GitHub starts this workflow late as a rule (median gap 209 minutes over its first 95 runs, maximum 396), so a due minute outside the last five was dropped silently. `a-late-tick-drops-a-cron` characterised it; the same file, renamed, now proves the catch-up.

### Design

- **Boundary.** A new step reads the previous successful *scheduled* run of this workflow (`gh api repos/…/actions/workflows/cron-dispatch.yml/runs?status=success&event=schedule&per_page=5`, the current run excluded by id, `run_started_at` taken) under `permissions: actions: read`, and passes it to the dispatcher as `CRON_SINCE`. Only scheduled runs count, because a manual `--route` run dispatches one route; taking it as the boundary would skip every other route due since the real previous tick. A lookup failure, an empty result or an unusable value never fails the tick: the step prints why and hands over an empty boundary, and the dispatcher runs its fixed five-minute window exactly as before, saying so in its own log line.
- **Window.** `tickWindow(now, since)` evaluates `(start, now]` in whole minutes, with `start = max(min(since, now − TICK_MINUTES), now − CATCH_UP_MAX_MINUTES)`. It never narrows below the fixed window, so a boundary two minutes ago (a quick pair of runs) costs nothing. A missing, unparseable or future boundary leaves the fixed window alone and is named in the log (`; CRON_SINCE ignored: not a timestamp` / `in the future`).
- **Cap, and why it clamps rather than discards.** `CATCH_UP_MAX_MINUTES = 1440`. Every route the catch-up serves fires more than once a day (that is the rule that admits it), so it has a due minute in any 24-hour window and a wider window cannot add a route — only minutes to scan. A boundary older than the cap is therefore *clamped* to it: a `since` from weeks ago (a workflow re-enabled after being disabled) yields a 24-hour window, which fires every sub-daily route once. It is not discarded, because discarding would drop the catch-up on exactly the longest gaps — the measured maximum of 396 minutes already exceeds six hours — and the clamp costs at most one call per sub-daily route. A test computes each sub-daily route's longest gap over a week and fails if one exceeds the cap, so a route that fires less often than daily-but-not-once-a-day cannot be added silently.
- **Once per route.** A route is called at most once per invocation however many of its minutes fell in the window: the routes are sweeps over pending work, not replays of one slot. This recovers the lost *firing*, not the *rate*; a `*/5` route still runs once per tick, so `a-cron-cadence-is-a-promise-nothing-keeps` is unchanged and still true.
- **Daily routes are not caught up.** `isSubDaily(expr)` — `!(minute.size === 1 && hour.size === 1)`, the negation of Vercel Hobby's rule — decides. Its complement is exactly the set `vercel.json` mirrors at the dispatcher's own minute (a test now pins that equivalence), and Vercel fires on time; a catch-up hours later would be a second daily run, for `admin-digest` a second email. Those routes keep the fixed window, so `admin-digest-replay-contract`'s pin (`dueRoutes` selects it at 12:30–12:34 only) holds, and the known same-minute double send is neither added to nor removed.
- **Log.** `cron-dispatch at <now> (window 187 min from <start>): …`. With no boundary the line is byte-identical to before; `--route` runs ignore the boundary.

### 2026-10-03, later — a tick that could not find its boundary is not one (review 5969190760 on #699)

**The edge.** The boundary step swallowed every lookup outcome into "dispatch the fixed window and finish green", and the step that reads boundaries takes only `status=success` runs. So a tick whose lookup *failed* (a 403, an outage, an unexpected shape) dispatched its five minutes, finished green, and was taken by the next tick as the boundary: last covered 03:00, the 09:07 lookup fails and dispatches five minutes, the 12:07 lookup works and catches up from 09:07 — 03:00 → 09:07 never recovered. The record above said a lookup failure "never fails the tick"; it was right about the dispatch and wrong about the run.

**The fix.** The step now tells the two look-alikes apart. The API answered and there was no previous scheduled success — the first tick ever — is `lookup=ok` with an empty boundary and starts the chain. The API did not answer, or answered something unusable, is `lookup=failed` with an empty boundary. The dispatch step runs either way, unconditionally, so nothing due this tick is skipped. A last step then fails the run when `lookup=failed`, with an `::error::` saying why: the boundary query's existing `status=success` filter makes a run failed on purpose invisible to the next tick, which catches up from the last real success instead — within the 24-hour cap, repeating the failed tick's five minutes for routes that are idempotent sweeps, losing nothing. A lookup that keeps failing keeps dispatching and keeps the workflow red, which is what a broken `actions: read` permission should look like.

**Test.** `tests/a-tick-that-could-not-find-its-boundary-is-not-one.test.ts` extracts the step's `run:` block from the YAML by indentation and executes it under `/bin/bash -eo pipefail` with PATH reduced to one directory of the test's own: a fake `gh` that answers from a fixture body the way the API would (the `status`/`event` query filters applied, the step's own `--jq` expression evaluated by the real `jq`) and symlinks to `date`, `jq` and `sed`, so the machine's `gh` cannot be reached and the absent-`gh` case is proved by `command not found` from the step's own stderr. A well-formed previous start is the boundary (`lookup=ok`); no run, or only the current run, starts the chain (`lookup=ok`, no boundary); a 403 and an absent `gh` are `lookup=failed` with no boundary and exit 0 (the step itself never fails, so the dispatch still runs). The run-level half is pinned on the YAML: the dispatch step follows the boundary step and carries no condition, the failing step follows the dispatch, is conditioned on `lookup == 'failed'`, exits 1, and the boundary query still filters on `status=success`.

**Refinements (review 5970787916 and 5970791078 on #699).** Two look-alikes inside "ok" were still conflated. (1) The `--jq` expression mapped a selected run whose `run_started_at` was null or missing to an empty string, which the shell read as "no previous run": the first-tick bootstrap. The expression now answers one word per outcome — `none` when no run was selected, the timestamp when it is a string, `unusable` otherwise — and only `none` starts the chain. (2) A shape-valid start in the future passed as `lookup=ok`; the dispatcher's `tickWindow` then ignored it and fell back to five minutes while the run finished green — the same incomplete boundary by another route. The step now applies the two tests `tickWindow` applies (a real timestamp, per GNU `date -d`, and not after now), so a boundary the step accepts is one the dispatcher uses; anything else is `lookup=failed`. The step's stderr is no longer discarded, so the API's own error line reaches the job log. Tests: a null start, a missing start, a non-timestamp, a future start, a body with no run list and a null body are each `lookup=failed` and never "starts the chain"; the step's accept/refuse decision is checked against `tickWindow`'s on the same values; and a **three-run regression** replays the review's chain — A succeeded at 03:00, B at 09:07 failed itself, a manual run at 11:00 is excluded by event, and the 12:07 tick is given A, so `tickWindow` covers 03:00 → 12:07 (547 minutes, uncapped) — with the negative control that a green B would have moved the start to 09:07 and lost the gap. GitHub is not known to emit a null, missing or future `run_started_at` for a completed run; the cases are bounded regressions, not observed behaviour.

**Refinement (review 5971121597 on #902).** "No previous scheduled success" was still read as the first tick. `status=success` is a filter the API applies over the whole history, so its empty answer is as true of a workflow whose every tick so far failed or was cancelled — a 09:07 whose own lookup failed and failed itself, a tick that died on a blank `CRON_SECRET` — as of a first tick; the 12:07 tick then dispatched five minutes, finished green and became the next boundary, and 09:07 to 12:07 was never caught up. The step now asks twice, in order: the success-only question, and on `none` every previous scheduled run of any conclusion (the hundred most recent, the current run excluded by id). No previous run at all is the first tick and starts the chain as before. Previous runs with no success among them make the **oldest usable start** the boundary (`lookup=ok`): no successful tick has covered a minute after it, and a failed or cancelled run dispatched at most its own five minutes, so this over-covers and never under-covers (idempotent sweeps; the dispatcher's one-day cap applies). Previous runs with no usable start at all are `lookup=failed`. The review proposed the fixed window with no boundary for failed-only history; that rule could never be left — no tick can succeed until one has — which is why the oldest recorded tick is taken instead, and the next green tick is the boundary. Tests (+6 in the same file): the review's chain (09:07 failed → the 12:07 tick catches up 180 minutes from 09:07 and does not "start the chain"); several failed and cancelled ticks take the oldest usable start; a manual run is in neither question; failed runs with no usable start are a failed lookup; a success wins over failures before and after it; the first tick ever still starts the chain and the second question is asked only inside the `none` branch. Mutation control (the `none` branch made to start the chain again): 5 failures.

### 2026-10-04 — the step is a script (#952)

Main's #952 (`codex/cron-history-pagination-20261004`) replaced the boundary step's shell with `scripts/cron-run-history.mjs`, and this branch takes it as it landed. The script asks the same questions in the same order — the previous scheduled success; on none, every scheduled run of the last day; on none, whether anything older exists — and settles what the shell could not: a day of five-minute ticks is 288 runs and an API page holds 100, so the shell's single `per_page=100` page could not see the oldest run of a full day of failures; the script follows the API's Link pagination over the bounded day and clamps anything older to the 24-hour floor the dispatcher would clamp it to anyway. A run that never recorded a start counts from its creation time (earlier, so the window over-covers). A lookup that failed is `lookup=failed` as before, and the last step fails a *scheduled* run on it; a manual run is not failed for a lookup it does not use.

`tests/a-tick-that-could-not-find-its-boundary-is-not-one.test.ts` is the reviews' cases, re-aimed at the script's `discoverCatchUpBoundary` through a fake Actions API that applies `status`, `event` and `created` and pages the way the real one does: the previous success as boundary; no run / only this run as the start of the chain; a null, missing, malformed or future start, a body of another shape, a 403 as failed lookups; the step's accept/refuse decision checked against `tickWindow`'s; the three-run chain with its negative control; the failed-only history taking the oldest run, across three pages for a full day, clamped when older than the cap, manual runs in neither question; a success winning over failures around it; the first tick's three questions in order. The run-level pins on the YAML stand: dispatch before the failing step, the failing step conditioned on `lookup == 'failed'`, the dispatch step unconditioned, the boundary step running the script that filters on `status=success` and `event=schedule`.

### Still open
