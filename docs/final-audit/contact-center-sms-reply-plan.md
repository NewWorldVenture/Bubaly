# Contact Center SMS automatic reply: proposed reservation design

Design only, 2026-09-12. Reviewed the SMS checkpoint `f51bcd40b8d17072b92851facaf371e0ac5319c5` and the existing urgent-delivery/schema/Trust contracts. This document changes no application, test, provider or audit state. The existing replay characterization remains a known failure, not a workflow PASS.

## Recommendation and exact guarantee

Use a dedicated, unregistered `contact_center.sms_reply` receipt in service-written `ai_tool_calls` as the authority to emit TwiML. Preserve the first **committed** reply candidate, then permit only a checked `queued → emission_reserved` compare-and-set (CAS) to return `<Message>`. A deterministic outbound inbox row is its display projection, not proof of a send. Once emission has been reserved, no retry or age-based recovery may emit that reply again.

This deliberately permits a missed reply if the process dies after reservation but before returning TwiML. The application cannot distinguish that crash from a response that reached Twilio and was processed. A returned `NextResponse`, or a socket-finish event, is not provider acceptance or handset delivery. Until an independently verified provider status callback exists, the durable status must remain **confirmation unknown**, including apparently successful local response construction. Twilio documents status callbacks with a Message SID for `<Message>`; adding and validating that receipt is a separate bounded extension. [Twilio Message verb](https://www.twilio.com/docs/messaging/twiml/message).

## Current source evidence

- `app/api/contact-center/sms/route.ts:73` runs the concierge again on every callback. Lines90–108 use `ai_handled` only to decide planner recovery. Lines114–117 unconditionally insert an outbound row and return `<Message>` whenever the current result permits a reply. The existing test at `tests/contact-center-callback-boundary.test.ts:242` observes two reply emissions and two outbound rows for one inbound SID.
- `lib/contact-center/server.ts:408` inserts an outbound inbox row without a provider reference or returned identity. Its exception check cannot establish an exact saved receipt.
- `supabase/migrations/0214_family_contact_center.sql:36–58` provides inbox UUID primary keys and a **global**, partial unique index on `(channel, provider_ref)`. It has no reply phase, delivery receipt, revision, metadata or `updated_at`. `status` means `new/read/archived`, and the existing family-scoped status action lets members change it; it must not become emission authority.
- `0250_ai_runtime_core.sql:289–323` supplies private system-ledger identity, bounded JSON payloads, state, attempt, timestamps and a unique family/idempotency key. The existing urgent delivery module demonstrates a separately namespaced receipt and revision-fenced transitions, but its queued SMS REST retry rules must not be copied into TwiML emission.
- `ai_handled=false` is also **not** evidence of no previous reply: non-actionable messages can return before the planner stamp, yet the SMS route still replies. Legacy uncertainty applies to every preexisting inbound row without the new receipt, especially handled rows.

## Receipt and authority

The key should be `contact_center.sms_reply:<sha256([familyId,"sms",inboundProviderSid])>`, with a deterministic UUID primary key derived from that entire namespaced key. Require a validated canonical SM/MM SID for automatic replies; capture without one can retain the existing intake fallback, but must not infer a unique reply occasion from a body-derived hash. Two genuinely separate identical messages are not necessarily the same reply occasion.

Proposed versioned, strict payloads:

- Immutable inputs: family ID, channel identity/current-number snapshot, inbound SID, exact sender/destination, bounded original body or its checked capture reference plus fingerprint, frozen summary/intent, final reply text, locale and reply-policy version. Save the urgent saved-inbox wording before reservation when appropriate. A legacy/suppressed receipt may have no reply text; queued/emission phases require a nonempty validated bounded string. The text is validated/escaped once from this snapshot and never regenerated after planner failure; no credentials, headers, provider diagnostics or unrelated household context belong in it.
- Outputs: `version`, random `revision`, `phase`, canonical inbound/outbound IDs when available, an allowlisted reason and an emission token/timestamp. Suggested phases are `queued`, `emission_reserved`, `unknown`, `suppressed`, `legacy_unknown`. None means delivered. `emission_reserved` and `unknown` share the same externally visible “confirmation unknown” meaning and are permanently ineligible for automatic emission.
- Row identity: exact `tool_name`, `actor_kind='system'`, null requester/member/run/step/request/conversation/AI-message references; `resource_table='family_inbox_messages'` and the verified inbound ID once attached. Validate the loaded row, deterministic ID/key, family, payload version, binding and phase on every read. Never trust a colliding primary key or a 23505 by itself.
- Insert plainly, then resolve only a verified 23505 with an exact checked read. Neither the inbox partial index nor the ledger partial index justifies a bare PostgREST `onConflict` target. Using the deterministic primary key is possible, but duplicate-ignore still needs a complete exact read. Bound each new SDK request with an actual abort signal and disable automatic request retries; validate counts/receipts and never let a late result change an already retired emission decision.
- Every mutation matches ID, family, tool, observed state and the previous random JSON revision. All transitions create a fresh revision. `queued → emission_reserved` additionally checks phase, immutable fingerprint and zero prior emission attempts; its successful exact receipt is the only authority to produce one `<Message>`. A transport error or unusable CAS receipt produces no message. If the write actually committed, later readers hold it as unknown.

Keep this tool outside the registry and generic executor. `lib/ai/tools/execute.ts` contains stale reservation takeover and ID-only finalization semantics intended for its existing tools; neither is safe for a possibly consumed TwiML response. Literal namespacing plus null execution references avoids conflating these rows with current run-bound execution, approval replay or metric proof. Existing consumers must be rechecked in the implementation tests, not assumed safe forever.

## Proposed callback order and recovery

1. Keep the existing bounded signature verification and Advanced Opt-Out STOP/START/HELP early return. Before creating reply authority, also reject duplicate/non-string fields, conflicting SID aliases and invalid destination/sender data. Keep the configured callback origin authoritative.
2. Resolve the current family/channel through checked reads. Load the deterministic reply receipt **before** invoking the concierge. If it exists, verify the complete binding and use its frozen candidate; do not generate a second candidate. If absent, check for an existing inbound row. A preexisting row without a reply receipt becomes `legacy_unknown`; no timestamp/body matching against old outbound rows proves that it was never answered.
3. For a genuinely new occasion, run the concierge and commit the first candidate as `queued` **before inbox capture or any successful inbound acknowledgement**. Concurrent candidates race on the private key; the loser reads and uses the winner's validated original content. Persist `suppressed` instead when current policy intentionally forbids a reply. Do not later turn a suppressed occasion into a reply merely because the setting changed.
4. Capture/re-find the inbound message using frozen inputs and validate its exact family/channel/SID/direction/sender/destination/body binding. Attach its ID through revision CAS. Preserve independent urgent delivery and planner recovery; planner calls use the saved intent/body and existing provider-ref key. A planner failure returns503 while leaving the original queued reply unchanged. Existing receipt phases never justify skipping still-required intake/planner recovery.
5. Before emission, re-read the current family/channel and verify that the same number still belongs to the same family and concierge replies are still permitted. Saved routing is context, not perpetual authority. Disablement, reassignment, spam or unsupported recipient transitions to `suppressed`, without a message. A failed read returns503. This cannot eliminate the final nontransactional race with a setting change after the read.
6. Ensure one deterministic outbound projection, then make the exact `queued → emission_reserved` CAS as the last required write before constructing the XML response. A loser or replay returns empty TwiML once required independent recovery succeeds. Unknown database state returns503 with no `<Message>`. Do not add a post-response “succeeded” stamp or reset held authority after a timeout.
7. An observed `emission_reserved` can be relabeled `unknown` through a fenced diagnostic transition, but no process may turn it back into queued by age. A worker can repair display projections or report a held reply; it cannot emit an old TwiML response outside the original inbound request. A REST SMS replacement would be a new explicitly authorized send path with a different receipt contract.

Missing receipts are not backfilled as “unsent.” If existing inbox rows, old unlinked outbound rows, malformed private data or unresolved collisions prevent proof, hold them with a specific review status. A rolling deployment still serving the old unfenced handler can bypass the new reservation entirely; a controlled cutover/drain of old handler versions is a deployment prerequisite, not something these database predicates can prove.

## Deterministic outbound row comparison

| Approach | What it establishes | Limitation |
| --- | --- | --- |
| Deterministic inbox UUID alone | One timeline row through primary-key uniqueness; exact body/recipient can be read back. | Row existence cannot distinguish queued preparation, reserved emission, consumed TwiML or lost response. Using insertion as the sole emission gate consumes the opportunity before planner recovery; moving insertion later loses the original candidate on planner retry. |
| Namespaced outbound `provider_ref` | Same deduplicated projection using the existing `(channel,provider_ref)` index. | The index excludes null and is global across families **and directions**. Reusing the raw inbound SID collides with the inbound row. Use a purpose/family-derived namespace and verified insert/read; the reference is an application key, not a Twilio Message SID. |
| Private ledger plus deterministic projection — recommended | Stores the original candidate and separate emission authority, with exact CAS ownership and explicit held/suppressed phases. | Adds checked reads/writes and a small presentation contract. It still cannot make the database and provider response atomic. |

Prefer a deterministic outbound UUID and a clearly namespaced synthetic provider reference for traceability. Insert the projection without overwriting on conflict, then verify family, channel, direction, destination and frozen body. Preserve any later read/archive status and existing timestamps. Do not encode reply delivery in `status`, `ai_handled`, `ai_intent` or `ai_summary`, and do not claim that the projection was sent merely because it exists.

## Privacy and honest presentation

Both inbox and ledger writes are service-only in these schemas. The inbox is family-member-readable; a null-requester system `ai_tool_calls` row is readable only to managers under `0250:410–413`. It is private application state, not a secrets vault. Keeping a bounded copy of already readable intake/reply text there does not broaden that data's access. Never return the private JSON payload directly to the browser.

The present generic Trust view is insufficient: `loadRecentToolCalls` selects no reply phase; `trust-activity-tab.tsx:219–234` renders reserved as “Started” and shows `error` only for failed rows. Do not label the receipt succeeded merely to make the ledger look finished. Persist only safe translated diagnostics, and add a bounded, family-authorized **display-only reply-status DTO** to the Contact Center page/module. Its labels should distinguish “Reply prepared,” “Reply confirmation unknown — no automatic repeat,” “Previous reply status unknown,” “Reply suppressed,” and “Reply status unavailable.” Load only status for the displayed family/message IDs; no authorization tokens or raw receipt inputs/outputs are exposed. A status read error remains visible, while independently verified inbox content remains readable.

No automatic retry control should appear for held/legacy outcomes. A future manual follow-up must be an explicit new operation with its own authorization and identity; archive/read actions must never reset emission authority. Family members already allowed to read an inbox row may receive its minimal display status; raw private receipt access remains manager-only.

## Bounded implementation and meaningful checks to authorize later

Proposed ownership: new `lib/contact-center/sms-reply.ts`; the SMS-only orchestration in `app/api/contact-center/sms/route.ts`; additive status loading/type in `app/(app)/dashboard/contact-center/page.tsx`; status rendering in `components/modules/contact-center-module.tsx`; focused new receipt/query tests plus the existing callback replay characterization converted to desired assertions; seven base locale additions by the catalogue owner. Keep shared outbound email/voice helpers, urgent receipts, SQL, global navigation and generic tool execution unchanged.

Required executing cases: duplicate and simultaneous callbacks emit at most one Message; planner failure/retry preserves the first committed reply even when a second classifier answer differs; failure/lost response at each receipt/capture/projection/CAS boundary; crash after reservation before response and discarded response both prohibit replay; returned and thrown reads fail visibly; cap-hidden/mismatched identities fail closed; legacy handled **and unhandled** rows never imply unsent; disabled/reassigned numbers suppress; urgent delivery and planner retries remain independent; read/archive markers survive projection repair; provider controls and signature rejection still bypass reply work; invalid XML/body bounds cannot consume authority unnoticed. Use actual middleware/route execution and installed PostgREST transport with faithful uniqueness/count/CAS fixtures, plus actual React status rendering and family-bound read-denial tests. None substitutes for deployed PostgreSQL/RLS or real provider evidence.

Operational limit: this reservation fixes duplicate emission, not durable delivery or slow synchronous intake. Twilio's default callback budget is 15 seconds, and HTTP 503 retry depends on provider configuration. A queue persisted before slow AI and a separately verified delivery-status endpoint are distinct follow-ups. [Twilio webhook connection overrides](https://www.twilio.com/docs/usage/webhooks/webhooks-connection-overrides). If status reporting is added later, Twilio recommends setting both `<Message action>` and `statusCallback` to the same URL for account/SMS/MMS compatibility; that endpoint must validate signatures and bind provider SID, sender/destination and the original reservation before changing any status. [Twilio Message callback attributes](https://www.twilio.com/docs/messaging/twiml/message).
