# Explicit logout and newer-login preservation

This cycle implements AUTH-L06 from `auth-signout-race-plan.md`, starting at published `e0abcbeb`. Full committed-source gates and current-source hosted verification are recorded separately after source freeze; the focused evidence below is not a complete production workflow sign-off.

All six web sign-out forms now use a shared browser form. It captures the account/session visible when mounted or when confirmation opens, prevents duplicate and retired submissions, and requires explicit review before a changed account can be signed out. Normal token rotation within the same session remains valid. The helper reads current cookies, compares intended identity, synchronously clears only the configured project's captured session/auxiliary cookies and verifies the deletion. Readable malformed cookies remain clearable; denied cookie access or rejected writes never claim success. A session already absent still advances the logout generation to fence older renewal work.

Local cache retirement, session reconciliation and an explicit public Realtime token update occur before any provider wait. Revocation uses the installed public `AuthAdminApi.signOut` with the exact captured JWT, public API key, omitted browser credentials and an eight-second deadline. No session client, refresh or storage mutation belongs to that transport. Local is the default scope. Provider failure or timeout is recorded as unconfirmed; no later response deletes cookies, purges replacement data or navigates a new login. The form routes only while current browser storage is still signed out.

The ordinary browser client's public cookie adapter uses a durable token-free logout generation. A renewal started before logout cannot publish a stale successful token or a delayed definitive-failure deletion after that generation changes. Failure-body delivery and the later cookie-commit boundary are checked separately. A valid current-generation rejection still ends an invalid session; an explicit SDK logout carrying the exact current token remains usable. Server rendering uses the prior cookie adapter. The ordinary browser factory uses the SDK's exported `processLock` to serialize overlapping reads/renewals in the same realm: the installed SDK could otherwise leave a coalesced caller unresolved when a guarded removal throws inside error cleanup. Both callers now settle, the queued current B session renews, and subsequent explicit logout still works. No SDK internals or packages were modified.

Other tabs receive only a request to reread storage. BroadcastChannel and storage fallback use a deduplicated nonce without identity or credentials. A local change invalidates older reads immediately and bypasses the 30-second lifecycle throttle. Successful null receipts and SDK `SIGNED_OUT` events require fresh cookie absence before cache retirement or forwarding. A stale event with B cookies schedules one bounded local reconciliation, without rebroadcast loops. Accepted session receipts update Realtime only if their exact token still matches current cookies; signed-out reads require fresh absence before downgrading to the public key. No synthetic auth events are emitted.

## Compatibility POST

`POST /auth/signout` remains available for a form submitted before hydration. It rejects cross-origin submissions, reads the submitted project's candidate without refreshing, and attempts token-specific revocation. Its response never writes authentication cookies. A short-lived HttpOnly cookie carries only a random nonce, intended user/session comparison, expiry and revocation outcome. The redirect to `/auth/signout/complete` binds the nonce. That page's browser helper automatically clears only the matching intended session; B, missing/mismatched receipts and expired receipts cannot be automatically signed out. The one-minute receipt does not authorize server access and contains no bearer or refresh token.

Both exact logout middleware paths skip ambient refresh, preventing that layer from attaching stale auth cookies. The completion page uses the existing auth layout and no shared navigation changes. The compatibility path now requires JavaScript to finish local cookie deletion; its translated no-script message explains that requirement. HTTP cookie deletion cannot conditionally target a browser identity changed after a response was prepared. The normal hydrated controls clear immediately, without this redirect bridge.

## Remaining boundaries

Browser cookie comparison/write is not atomic across processes. Unrelated server responses can still restore stale credentials; this cycle removes auth writes from the logout response and fences the ordinary browser renewal path, not every response in the application. Auxiliary verifier removal from an already delivered SDK operation has no public operation identifier. Isolated signup/recovery clients retain their separately tested ownership guards. Production session policy, physical mobile reopen, actual provider revocation and the complete deployed logout journey remain unverified. The disposable hosted Auth journey now follows the compatibility completion in a real page before checking cookie removal and another device's surviving session; it must pass on the published source before that path is claimed verified.

Five translated notices were appended to each of seven base catalogues. All 13,556 prior entries, values and order were preserved. SQL, dependencies and shared navigation are unchanged. AUTH-002 remains IN PROGRESS pending full source gates and the remaining production boundaries.
