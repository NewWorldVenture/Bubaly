# Delayed sign-out response: open repair

Implementation update: the repository now contains the guarded local logout, token-specific transport, cross-tab reconciliation, renewal fence and cookie-free compatibility POST described in `auth-signout-cycle.md`. The original plan below is retained as the discovery record. Full source/hosted gates and remaining boundaries must be checked before complete workflow sign-off.

AUTH-L06 remains IN PROGRESS. An actual route/SDK/Chromium probe held account A's `/auth/signout` response, signed in B, then released A's response. Its fixed-name `Set-Cookie` deletions removed B's credentials. Cache reconciliation eventually retired B's data, but could not recover those credentials. Replacing the route with ordinary SDK `signOut()` alone does not fix this: the installed SDK awaits provider revocation before unconditional local removal.

The next bounded implementation must capture the intended account and project cookie state, perform guarded local deletion before any provider await, verify deletion and prevent late revocation results from clearing or navigating a newer login. Provider revocation can use the public `AuthAdminApi` export from `@supabase/supabase-js`: instantiate only the admin transport with the provider auth URL and public API key, then call `signOut(capturedAccessToken, scope)`. The method accepts the session's JWT; no service-role credential, cookie storage, refresh timer or session client is required. Use a bounded, cookie-free request; keep credentials in memory. Default scope remains local.

Six web forms require inspection and coordinated migration: `SignOutButton`, `StepUpForm`, `PrivacyCenter`, `AccountClosedGate`, `AppLockGate` and `TrialPaywallGate`. Shared navigation does not need editing. Session-change notifications must request a fresh cookie reconciliation, rather than asserting an authoritative `SIGNED_OUT` event that could retire a newer B. Cover cache, SessionKeeper, Realtime and recovery subscribers, including absent BroadcastChannel/storage and the existing 30-second focus coalescing window.

The legacy server POST remains a separate boundary. Keeping its current deletion response leaves the original reproduction possible. A new cookie-free protocol also needs an exact middleware exclusion to prevent ambient refresh headers. No-JavaScript POST cannot conditionally delete fixed-name cookies against the browser's later identity using HTTP alone; that behavior needs an explicit design before claiming complete repair.

Required execution cases include held success/error/timeout revocation with a later B login; changed identity before confirmation or deletion; stale inter-tab notifications; cancellation/repeat clicks at all six controls; cookie-write failure; large/chunked sessions and auxiliary/verifier ownership; unrelated project cookies; and actual route/middleware response headers. Also hold older refresh operations before and inside storage commit: manual deletion does not increment the SDK's private removal epoch, so an older renewal must not resurrect A. Older unrelated SSR responses can also restore credentials and remain a distinct boundary.

Fresh browser cookie comparison followed by deletion is not atomic across browser processes. A repair must state which races it actually prevents and must not claim distributed transaction semantics. This document is a read-only implementation plan; no sign-out production change or provider operation was made in this cycle.
