# PUSH-002 — FCM HTTP v1 and direct APNs delivery

2026-09-12. Baseline `c7b56eff`; edits began after root created `finalaudit.md`. No provider credentials were read, no external notification was sent, and no SQL or dependency was changed.

## Problem and implementation

The baseline used retired FCM `/fcm/send` authorization and routed every native device through it, including raw APNs registration tokens. `components/native/push-registrar.tsx` records Android as `fcm` and iOS as `apns`. The token distinction is documented by [Capacitor Push Notifications](https://capacitorjs.com/docs/apis/push-notifications); changing only the Firebase endpoint would leave iOS broken.

`lib/server/native-push.ts` implements independent provider transports. `nativePushConfigured()` reports configuration presence and shape for each provider; it does not validate live credentials. `sendNativePush(provider, token, payload)` returns `sent`, `failed`, `unconfigured` or `unregistered`. Root's `lib/server/push.ts` integration routes each stored provider explicitly and retains unsuccessful deliveries for retry.

- **FCM:** exchanges an RS256 service-account assertion at the fixed Google OAuth endpoint, with the Firebase messaging scope and a one-hour maximum assertion lifetime. It sends the resulting bearer token to the fixed FCM HTTP v1 project endpoint. Concurrent exchanges share a promise; cached tokens refresh before expiry and are keyed by the credential fingerprint. Old exchanges cannot overwrite a rotated cache. A 401 invalidates the matching cached token for the next queued retry. Successful replies must include the documented message name. The implementation follows [FCM HTTP v1 sending](https://firebase.google.com/docs/cloud-messaging/send/v1-api) and [Google service-account OAuth](https://developers.google.com/identity/protocols/oauth2/service-account).
- **APNs:** signs ES256 provider tokens with a P-256 key and sends raw hexadecimal device tokens directly over HTTP/2 to fixed production or sandbox Apple hosts. Provider tokens refresh after 50 minutes. Sessions are reused, released after five idle minutes, and replaced on credential/environment rotation. Requests include the alert push type and configured app topic. Stream/connection errors, closure and GOAWAY resolve pending sends as failures; the 15-second deadline cancels and destroys a stalled connection. This follows Apple's [token authorization](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns), [request format](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns) and [response handling](https://developer.apple.com/documentation/usernotifications/handling-notification-responses-from-apns). Current official Markdown representations of those Apple pages were inspected because their HTML pages require JavaScript.
- **Boundaries:** external response bodies are bounded to 64 KiB; serialized notification payloads are capped at 4,096 bytes. Fixed provider hosts and validated project/topic/device-path fields prevent using configuration or registrations as arbitrary destinations. Fetch redirects are rejected. Authorization exchanges and provider requests have 15-second deadlines. Only a typed FCM `UNREGISTERED` error with HTTP 404 or APNs HTTP 410 `Unregistered` permits pruning. Generic invalid arguments, project/permission errors, rate limits and server failures retain the registration. Provider response bodies, credentials, device tokens and notification contents are never logged by this helper.

The native-only block in `.env.example` now names `FCM_PROJECT_ID`, `FCM_CLIENT_EMAIL`, `FCM_PRIVATE_KEY`, `APNS_TEAM_ID`, `APNS_KEY_ID`, `APNS_PRIVATE_KEY`, `APNS_TOPIC` and `APNS_ENVIRONMENT`. Private keys are server-only PEM values and may use literal backslash-n separators. APNs defaults to production; sandbox is explicit. The old `FCM_SERVER_KEY` is no longer consumed. These are follow-up additions to the discovery inventory's baseline environment names, not claims about values configured on any host. Root also updated `docs/mobile.md` with deployment setup and retry limits.

## Remaining verification and limitations

The repository implementation and controlled transport execution are locally verified. **The real-provider and physical-device workflow remains unverified**: an authorized Firebase project/service account with FCM HTTP v1 enabled, native Android Firebase registration/configuration, an Apple push-enabled App ID and matching team/key/topic/provisioning environment, deployed server secrets, and actual Android/iOS registrations are required. Verify provider acceptance, foreground/background presentation, notification tap routing, permission denial/re-enable, token rotation and uninstall invalidation on supported physical devices. Live registration data and PostgreSQL device ownership/RLS checks remain separate from these transport fixtures.

`sent` means provider acceptance, not proven device receipt. No per-device durable receipt or distributed worker claim was added. Partial delivery, lost acknowledgements or overlapping cron workers can repeat sends; `PUSH-003` remains open in the root [push cycle](push-cycle.md). The bounded transport changes do not close that schema/concurrency guarantee. Production readiness remains **NO**.
