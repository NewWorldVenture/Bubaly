These controls do not erase the failures above.

## Original bounded repair proposal

Require both catalog and log reads to be usable before deriving actionable progress, distinguish loading/error/stale states, and use the existing ErrorState retry. Gate rendered controls and retained handlers. Keep current family/member/habit/day and current rows in a lifecycle-aware owner reference; use a synchronous pending-write guard and contained try/finally cleanup. Preserve form drafts on read retry. Retire callbacks after family/access change or unmount, and recompute/validate the current day at action time with a rollover trigger.

Readback must confirm that the relevant current request committed usable rows before unlocking another relative amount edit. The existing hook's `refresh(): Promise<void>` also resolves on error or supersession, so merely awaiting it is insufficient; a repair needs an explicit committed/current outcome or equivalent caller-side verification. Keep conditional family/habit/date/count predicates and require a matched row for count updates/deletes so a concurrently changed total is reviewed/refetched rather than overwritten. Existing uniqueness prevents duplicate inserts but does not make read-modify-write increments atomic. Cross-client atomic increment semantics remain a server/database obligation; no SQL repair is authorized here.

The preset's existing clinical target values, localization gaps, arbitrary-target validation, AI coaching, archive/edit form races, reminder scheduling, and timezone-policy selection were not expanded into this execution scope.
