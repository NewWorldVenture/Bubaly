## Prioritized repository findings

### OPS-F01 — High — Resend failure is acknowledged as a successful duplicate on retry

Status: **Suppression retry FIXED + locally verified in `../resend-cycle.md`; full integration and transactional metrics remain open.** The following is baseline evidence: `app/api/webhooks/resend/route.ts:82` returns 200 for any recent `processing` row. Post-claim failures, including the suppression write at line 133, return 503 without releasing or marking that claim failed. A subsequent provider retry sees the abandoned `processing` row and receives 200 without performing the required suppression.

Executed the real handler after TypeScript transpilation in memory, with a valid fixture Svix HMAC and an injected transient `marketing_suppressions` error for `email.complained`. Result: first request 503; retry 200 `{received:true,duplicate:true}`; suppression attempted once; durable event remains `processing`. No network was involved. Required fix: unsuccessful claims must remain retryable, with ownership-safe reclamation; only completed work can acknowledge a duplicate. Also examine the unguarded stale-claim update at lines 87–90, non-atomic counter read/update at lines 116–121, and ignored automation failure at line 151. Existing `resend-webhook-replay-contract.test.ts` inspects strings and does not catch this execution failure.

### OPS-F02 — High — Push failures are permanently marked delivered; read/stamp errors can report success

Status: **Failure retention FIXED + locally verified by root in `../push-cycle.md`; real delivery and distributed receipts remain open.** The following is baseline evidence: `lib/server/push.ts:207` stamps `pushed_at` after every attempted fan-out, including provider failures and missing provider configuration. `sendPushToUser` ignores the device lookup error at line 68; `membersOf` logs but converts a member lookup error into an empty audience at line 178. The stamp error itself is logged without incrementing failures at line 208.

Executed the actual module in memory with provider/Supabase fixtures: failed provider send yielded `failed:1` **and a delivery stamp**; device and member read errors each yielded zero failures **and a delivery stamp**; a failed stamp yielded `sent:1, failed:0`. Required fix: distinguish intentional audience exclusion/no devices from lookup failure/unconfigured delivery, preserve retryable work, surface stamp failures and verify concurrent overlapping dispatch. A read followed by a post-send stamp alone also does not substantiate the module's "never pushed twice" claim when Vercel and GitHub overlap.

### OPS-F03 — High — Native push uses legacy FCM and sends APNs tokens to the FCM path

Status: **Provider implementation FIXED + locally verified in `../native-push-cycle.md`; real provider and physical-device verification remain open.** The following is baseline evidence: `lib/server/push.ts:46` posts to `https://fcm.googleapis.com/fcm/send` using `FCM_SERVER_KEY`; its own comment says to replace it in production. The branch treats every non-webpush device alike. `components/native/push-registrar.tsx:46` stores iOS registration as `provider:'apns'`, so raw APNs registrations also reach this FCM sender.

Google's current [FCM HTTP v1 send documentation](https://firebase.google.com/docs/cloud-messaging/send/v1-api) requires OAuth2 service-account authorization and the v1 project send API. Microsoft's primary [FCM migration documentation](https://learn.microsoft.com/en-us/azure/notification-hubs/firebase-migration-rest) records legacy retirement in July 2024. [Capacitor v8 documentation](https://capacitorjs.com/docs/apis/push-notifications) distinguishes Android Firebase token registration and iOS APNs registration. No live sends were attempted. Repair provider-specific sending before marking the remainder blocked on Firebase/APNs provisioning and real-device testing. Supplying a legacy server key cannot close this repository defect.

### OPS-F04 — High — Family attachments remain public by URL

Status: **FAIL for family read-isolation requirements; source confirmed, live exposure not tested**. `supabase/migrations/0216_family_media_bucket.sql:22` creates `family-media` with `public=true`; its opening comment explicitly records this deferred privacy hardening. Consumers publish URLs with `getPublicUrl`, including `components/modules/messages-module.tsx:391`, `photos-module.tsx:123`, `reminders-module.tsx:638`, `components/memories/create-memory.tsx:105`, and the closet/inventory modules. Family-folder write policies do not protect public URL reads.

This requires a coordinated private-storage/read-URL transition and treatment of previously stored URLs. It cannot be declared fixed by changing one client helper, by proving authenticated SELECT policies, or by relying on unguessable paths. SQL/provider mutations are outside this lane's authorization. Root must retain the source defect and the exact constrained remediation separately; it is not merely missing credentials. Documents are a separate private bucket with manager restrictions for sensitive categories in migration 0266.

### OPS-F05 — High — Live social publishing has zero implemented connectors

Status: **FAIL / repository functionality incomplete**. `lib/social/connectors.ts:52` defines an empty `LIVE_IMPLS` object. Every configured platform returns `not_implemented`; missing credentials return `requires_setup`. Nine advertised provider definitions exist in `lib/social/capabilities.ts`: X, Facebook, Instagram, LinkedIn, TikTok, YouTube, Pinterest, Threads and Reddit. The pipeline truthfully records non-success, which does not complete publishing. Credential setup alone is insufficient. Drafting, internal feed/manual sharing and each platform's live posting workflow must have separate audit outcomes.

### OPS-F06 — Medium — Dispatcher can be green while no scheduled work runs

Status: **FAIL, source confirmed**. `scripts/cron-dispatch.mjs:141` returns normally when `CRON_SECRET` is missing; `.github/workflows/cron-dispatch.yml` documents that successful no-op. The route helpers correctly reject missing secrets, but this job never calls them. Missing scheduled delivery is therefore indistinguishable from a successful Actions tick unless logs are read. Fix repository-side failure visibility; separately verify matching secret/configuration on the two hosts.

The dispatcher examines only the previous five minutes (`dueRoutes`, line 102), with no durable last-success cursor. A delayed run at 11:08 excludes an 11:00 once-daily job; the existing matcher test explicitly demonstrates that. Vercel's daily secondary invocation helps some jobs but is not proof of catch-up or once-only delivery. `provider-sync`, `marketing` and `marketing-providers` allow 300-second handlers while dispatch aborts each request at 120 seconds. These are operational recovery/load test targets, not claims of a currently observed production outage.

### OPS-F07 — High investigation target — Allowance crash/retry gap

Status: **NOT STARTED for crash/concurrency workflow**. `app/api/cron/wallet-allowance/route.ts:72` advances the schedule before `creditChildWallet` at line 82. Returned credit errors restore it, but a killed worker between claim and credit leaves the due payment advanced. There is no per-period operation receipt in this path. `lib/wallet/server.ts:218` directly inserts wallet transactions. Existing tests prove selected claim/returned-error behavior, not process termination and persistent ledger recovery. Reproduce against an isolated database and design a durable operation before claiming exactly-once allowance delivery. No missing live credential explains this gap.
