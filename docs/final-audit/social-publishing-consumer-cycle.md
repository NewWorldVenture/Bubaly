# Social publishing consumer cycle — 2026-09-12

SOCIAL-002 was recorded by the audit owner before these consumer edits. This cycle covers Studio creation and review, the existing-post retry consumer, and detail/history rendering. It does not establish production readiness for the complete Social workflow.

The initial read-only review found no caller that resets publishing targets or deletes publish results before retry. `retryPublishAction` directly invokes `runPublishNow`. `cleanupPost` deletes a newly created post only before `publishStarted`; it preserves the post after a publication attempt begins.

The concrete duplicate path used a different identity: after an uncertain attempt, Studio kept the same Publish now action available and called `createPostAction` again. A real React/Chromium component fixture invoked the actual server action, current publish pipeline and installed Supabase/PostgREST against in-memory HTTP rows. The controlled connector returned an uncertain receipt. The first post remained `publishing`; a retained handler then created another post and called the provider again. The regression failed with expected provider calls **1**, received **2**, before the consumer source repair. The earlier exploratory fixture omitted PostgREST's `columns` parameter and was corrected before this reproduction was accepted as evidence.

The repaired Studio uses a synchronous pending/review guard. A saved post, including failed or uncertain publish outcomes, links to its existing detail and cannot be submitted as another new post by that mounted form. A create failure after `publishStarted` now returns the retained `postId` and publish action. A genuine pre-publish failure permits retry and preserves the draft. A lost action response shows a review-posts link and holds further creates because durable creation or provider acceptance may already have happened.

Detail withholds retry when the post or any target is publishing and for terminal post states. It explains awaiting confirmation and no longer labels an uncertain or failed history row “confirmed” merely because it lacks a permalink. The retry component guards concurrent callbacks, contains thrown action failures and reports existing uncertainty without claiming that another send occurred. Successful or uncertain outcomes disable its stale retry control.
