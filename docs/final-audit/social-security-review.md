# Independent social connection and publishing review

2026-09-12. Read-only review of the in-progress SOCIAL-001 X implementation and root-owned SOCIAL-002 pipeline, with synthetic execution of actual modules. The only application file changed by this reviewer is the separately authorized `lib/social/access.ts` (AUTHZ-002; see `social-access-cycle.md`). No SQL or live provider operations were performed.

## Source contracts and findings

`supabase/migrations/0034_social_command_center.sql` defines a unique social account identity `(family_id, platform, provider_account_id)`, but only a nonunique index on `social_account_tokens.account_id` and no unique `(post_id, account_id)` target constraint. Token tables have RLS and no user policy, while account/target metadata and statuses remain broadly family-writable under the migration. Permission checks before service-role token access are necessary; their required-read failure was reproduced and repaired in AUTHZ-002. The direct permission DELETE restriction bypass remains open as AUTHZ-003, a blocker before enabling live restricted-role publishing.

The new `lib/social/x-oauth.ts`, `account-tokens.ts`, `providers/x.ts`, and `app/api/social/x/callback/route.ts` bind the initiating user, active family, pending account, state, PKCE verifier, expiry, revision and configured callback into an encrypted continuation. A private canonical token receipt is claimed before the code exchange; cookie deletion alone is not the replay barrier. Callback identity is obtained from the provider before any connection is reported. Duplicate token rows and noncanonical token primary keys fail closed. Both encrypted credential envelopes contain account/family/platform/provider identity, which prevents swapping an otherwise decryptable credential to another account. This is stronger than copying the old sync callback: `lib/sync/oauth-state.ts` is only an opaque cookie equality helper, and the normal sync callback derives ownership from its current callback session rather than binding the initiating owner.

The callback uses configured origin and a fixed return path. The verifier is random, the challenge uses S256, duplicate state/code parameters fail, credential exchange uses fixed HTTPS provider endpoints, redirects are not followed, response bodies are bounded, and fetch has a deadline. Provider exception payloads and token-bearing responses are excluded from public errors and publish audit payloads. Automatic refresh is deliberately not implemented in this cycle: expired credentials require reconnect. Copying `lib/sync/accounts.ts` refresh logic would not provide serialization for rotating tokens across concurrent processes. A future refresh implementation needs a private claim before provider exchange and explicit handling of uncertain rotation; a compare-and-swap only after exchange is insufficient.

New X setup initially checked only presence of `SYNC_TOKEN_KEY`, while the shared crypto loader accepts arbitrary passphrases by SHA256 fallback. Following review, the API owner added `requireXConfiguration`: new X authorization requires the documented 32-byte hex/base64 key and nonblank app credentials. The legacy sync crypto behavior is preserved. This review did not inspect environment values or rotate any key; key entropy and custody remain deployment responsibilities.

## Reviewed races and controlled executions

1. **Private disconnect followed by failed public disconnect:** the first X source accepted an old OAuth callback when private tokens had become `blocked` but the public account still appeared connected with no `deleted_at`. Public deletion time therefore did not prove when private authority was revoked. The API owner added private `x_revoked_at` and rejects callbacks begun before/equal that revocation. An actual `account-tokens.ts` execution with a synthetic stateful compare-and-swap database confirmed the revised behavior: private revoke removed credentials, the public account intentionally remained connected, and the older callback failed `socialX.callbackInvalid` without restoring tokens. The owner maintains the permanent regression.

2. **Previously published duplicate account target:** the first pipeline checked duplicates only among eligible pending/failed targets. A published target and a failed target for the same account could be sent again; the original earlier-success test accidentally used this shape as a positive control. Root changed the check to count accounts across all targets and changed the positive control to distinct accounts. Actual `publish.ts` plus the repository `InMemorySupabase` confirmed the revised duplicate fixture fails before any connector send. This review saw the source defect and verified the repaired runtime; the root patch had landed before the independent execution, so this is not claimed as a separately captured failing test run.

3. **Stale parent status on no-op:** actual `publish.ts` plus `InMemorySupabase` reproduced parent `published` + sole target `pending` returning outcome `published` with target `pending`, despite zero sends. Root repaired the no-op result to derive the observed target status while preserving no writes/no sends and retaining an existing `publishing` claim. Independent focused verification passed: `npx vitest run tests/social-publish-execution.test.ts -t 'reports incomplete targets honestly'` — 1 test PASS / 27 skipped. A stale published parent with a pending target now reports `publishing` without dispatching it.

The source review also covered exclusive post status/revision claims, target claims tied to a job, canceled/replaced target fencing, provider confirmation validation, receipt-before-target persistence, retained claims after interrupted publication, and bounded keyset reads through an empty page. Post acceptance and database persistence cannot be made one transaction here. Transport loss, malformed/oversized/late confirmation and persistence loss therefore retain `publishing` for review rather than becoming ordinary retryable failures. Already materialized or dispatched provider requests cannot be recalled by a later local disconnect; this review does not claim immediate global revocation or provider-level exactly-once delivery.

## Primary provider evidence and limits

X documents PKCE authorization, exact callback matching, confidential-client authentication, and the `offline.access` refresh scope in its [OAuth authorization guide](https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code) and [user token guide](https://docs.x.com/fundamentals/authentication/oauth-2-0/user-access-token). Its [Create Posts reference](https://docs.x.com/x-api/posts/create-post) documents `POST https://api.x.com/2/tweets` and a successful 201 response containing `data.id`; no request-idempotency facility was found on that endpoint page. Unknown outcomes must therefore remain reviewable rather than being treated as proof that nothing was posted.

Initial unchanged focused checks: `npx vitest run tests/social-roles.test.ts tests/social-capabilities.test.ts tests/sync-oauth-csrf.test.ts` — 3 files / 19 tests PASS. Those tests did not expose the required-read authorization failure. AUTHZ-002 validation is separately recorded as 4 files / 49 tests, including 34 actual resolver/query-client cases. Root and the API owner own the changing pipeline/provider suites and final combined gates. No source-level or synthetic-provider result is a live-account workflow pass; app registration, credentials, provider entitlements, deployed RLS and real account behavior remain external verification dependencies.
