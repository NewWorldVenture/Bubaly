Other platforms, media kinds and recurrence must return a clear unsupported result before public persistence. Keep the existing immediate publishing implementation for other supported direct calls.

The instant must be in the future when scheduling is authorized. A later worker is allowed to dispatch overdue authorized work after downtime. Recurrence stays `none`.

## Public helper contract for root integration

These are server-only functions in new `lib/social/scheduled-publish.ts`:

```ts
createScheduledPublishReceipt({
  familyId, postId, scheduleId, scheduledFor, timezone,
  expected: { kind, body, link, accountIds },
}): Promise<{ receiptId: string }>

armScheduledPublishReceipt(receiptId: string):
  Promise<{ phase: 'queued' | 'approval_required' }>

publishScheduledPostNow(postId: string): Promise<PublishOutcome | null>

runScheduledPublishDrain({ now?, signal? } = {}): Promise<DrainSummary>
```

`create` obtains the request's authenticated context itself and requires current schedule permission. It uses the actual active member, ignoring any caller-supplied actor. Root passes the validated request fields; the helper checks exact current public row bindings and writes only `unarmed` authority. Root must obtain the actual schedule ID with checked insert/readback and finish calendar persistence before calling this helper. No worker executes unarmed authority.

`arm` authenticates the same initiating request actor again, rereads required public/approval/access state and atomically moves the private receipt to queued or held. **Once arm starts, root must preserve post identity on any ambiguous failure and direct the user to review; do not delete a post whose authority may already be queued.** A returned queued result means durable enqueue, not provider publication. A required-approval result means saved/held, not “Scheduled” as a promise of automatic dispatch.

`publishScheduledPostNow` authenticates the current requester and current publish permission. It returns null only when no private scheduling receipt exists, allowing root to preserve the ordinary manual path for unrelated posts. If a receipt exists, it shares the worker's private exclusive gate, snapshots the current manual requester as the protected execution actor, and explicitly permits executing before the due time. A manager with legitimate current publishing authority can manually publish another author's immutable schedule, matching the existing direct permission model; that is new authenticated execution authority, not trusting the old public creator. Dispatching/unknown/published receipts cannot be reset by a manual retry. Legacy scheduled posts remain visibly unverified; automatic dispatch never adopts them.

## Implemented contract clarification

The input stores the original **effective approval requirement** as a sticky boolean; `recurrence='none'` and the current approval state are checked from required public reads rather than duplicated as additional input fields. Private target proofs include the provider-confirmed timestamp. Outputs carry a bounded safe diagnostic key; public metadata uses `schedule_phase` and `schedule_error`, preserving `schedule_timezone` and unrelated fields.

Dispatch stops at70seconds and shared finalization stops at100seconds inside the110second route. Each query has a5second AbortError deadline; X requests retain their15second deadline. A durable UUID cursor traverses up to20 receipts per tick so future or held work cannot permanently block later receipts. Unknown/in-flight outcomes never regain send eligibility.
