# Reminder origin privacy rollout

This is an operator review and cutover plan, not authorization to change production. The last recorded production application is `06ac6e3b54cbd8da33bfa7ab10f0a860078cc5c9`; this release has not applied production DDL or configuration. Record the actual production version again before proceeding.

The release couples immutable reminder origins, guarded atomic writers and the application reader. Deploying the application before its schema makes required reads and RPCs unavailable. Installing the schema while old writers run can leave an OPEN card without its reminder: the old scan can save the card after its direct reminder insert is refused, and later scans skip that existing card.

## Coordinated cutover

1. **Approve a concrete maintenance mechanism.** The operator must name and approve how generated writes will be held across scheduled scans, on-demand scans, manual card acceptance, in-flight jobs and cached clients creating recurrence. Verify that the mechanism covers every entrypoint, drain in-flight work and record the start/version boundary. This document assumes no existing feature flag or toggle. If that hold cannot be established, stop before schema installation.

2. **Verify owner and privilege prerequisites.** Inspect actual table and routine owners, installed migrations, RLS, trigger order and function ACLs. The owner-routine creation path must satisfy the target reminder table's owner admission check; verify the `aa_require_trusted_origin` admission triggers and the complementary guards rather than assuming an owner named `postgres`. Ordinary authenticated and anonymous roles must have neither superuser nor RLS bypass. Private origin helpers must remain inaccessible to application roles. Authenticated callers may execute `create_card_family_reminder`, `create_card_legacy_reminder` and `repeat_card_family_reminder`; only the service role may execute `create_card_legacy_reminder_service`. Anonymous/public access and ordinary access to the service-only writer must remain refused. Verify the intended signatures, definer ownership and fixed search paths against the reviewed SQL.

3. **Install and verify the exact schema under the hold.** An authorized database operator must approve the actual migration procedure and inspect its complete apply list. The existing manual production migration workflow can apply unrelated migrations and backfills; do not dispatch it blindly. After the exact transaction succeeds, have the operator perform the approved Supabase/PostgREST schema-cache reload. Confirm that both reminder tables expose `autopilot_origin` and `autopilot_card_id`, the required RPC signatures are visible, and the installed ownership, grants and guards match the reviewed artifact. Keep writes held on any mismatch or reload failure.

4. **Reconcile the cutover gap.** Inspect OPEN cards created or attempted during the boundary, their actual source records, trusted reminder origins and any already committed reminder receipts. Record cards with no corresponding reminder or an inconsistent receipt. Do not infer trusted provenance from display payloads or public stamps, invent missing reminders, or retry in a way that rematerializes duplicates. Obtain an operator-reviewed disposition using the verified atomic writer and actual committed state; otherwise leave the affected work held for review.

5. **Release the exact coordinated application.** Record the approved immutable deployment commit and verify it contains the matching producer, reader, assistant recurrence, recurrence UI and database types. Replace server instances and jobs and require cached clients to reload into that release before allowing generated writes. Do not reopen the hold while any old writer or recurrence client can still act.

6. **Run production acceptance gates before resuming.** Using operator-approved accounts and synthetic records, verify a named member can read and resolve their generated reminder, an unnamed member cannot read or mutate it, another family's member cannot access it, and managers retain intended access. Confirm manual reminders still work. Reassign the actual source, refresh through the approved path and check the resulting audience. Complete and repeat a named generated reminder: verify one committed next occurrence, immutable card/family linkage, denied readers still denied, and a retry produces no duplicate. Include the real server asking-viewer path, ordinary acceptance, scheduled/on-demand writers and a reloaded recurrence client. Confirm failures return an error rather than a fabricated success. Record receipts and cleanup; resume only after every required gate and gap disposition is accepted.

## Failure and rollback

Keep generated writes held if installation, schema-cache refresh, deployment, ownership/ACL checks or acceptance gates fail. Before the schema transaction commits, abort using the approved procedure. After it commits, an old-application rollback is incompatible with the stricter origin admission and required RPCs; it can fail writes or strand cards. Do not remove privacy guards or erase immutable origins to make an old writer work. Any post-install recovery requires a separately approved compatible application/database plan, verification of existing receipts and a repeat of the acceptance gates. Application rollback alone is not a healthy recovery path.
