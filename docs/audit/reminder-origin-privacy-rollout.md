# Reminder origin privacy rollout

This is a review-only cutover plan. **Production is not ready for this rollout.** No production DDL, configuration, data, cache reload or deployment has been performed. The production application version has not been freshly verified; the historical recorded application was `06ac6e3b54cbd8da33bfa7ab10f0a860078cc5c9`.

The release couples immutable reminder origins, guarded atomic writers and the application reader. Deploying the application before its schema makes required reads and RPCs unavailable. Installing the schema while old writers run can leave an OPEN card without its reminder: the old scan can save the card after its direct reminder insert is refused, and later scans skip that existing card.

## Coordinated cutover

1. **Approve a concrete maintenance mechanism.** The operator must name and approve how generated writes will be held across scheduled scans, on-demand scans, manual card acceptance, assistant tools, completion updates, in-flight jobs and cached web/mobile clients creating recurrence. Disabling the autopilot tier is incomplete; both Vercel and GitHub schedule scans, and UI/assistant paths do not all consult that setting. A request timeout or client disconnect does not prove underlying writes stopped. Revoking only RPC execution does not hold parent completion updates. The isolated statement-barrier prototype still needs actual API/worker login evidence, a distinct authenticated maintenance session, reviewed deployment identities and impact scope, and composed acceptance. It also pauses manual writes; shared scheduler suspension can affect unrelated routes. Transaction drain alone does not prove a multi-request workflow is drained. Verify every entrypoint, drain work and record the version boundary. If that hold cannot be established, stop before schema installation.

2. **Verify owner and privilege prerequisites.** Inspect actual table and routine owners, installed migrations, RLS, trigger order and function ACLs. The owner-routine creation path must satisfy the target reminder table's owner admission check; verify the `aa_require_trusted_origin` admission triggers and the complementary guards rather than assuming an owner named `postgres`. Ordinary authenticated and anonymous roles must have neither superuser nor RLS bypass. Private origin helpers must remain inaccessible to application roles. Authenticated callers may execute `create_card_family_reminder`, `create_card_legacy_reminder` and `repeat_card_family_reminder`; only the service role may execute `create_card_legacy_reminder_service`. Anonymous/public access and ordinary access to the service-only writer must remain refused. Verify the intended signatures, definer ownership and fixed search paths against the reviewed SQL.

3. **Install and verify the complete approved schema under the hold.** An authorized database operator must first resolve the observed prerequisite gaps, approve the actual migration procedure and inspect its complete apply list and data effects. Neither existing release workflow is suitable without the execution review above. After the approved transactions succeed, have the operator perform the approved Supabase/PostgREST schema-cache reload. Confirm idempotency support, both tables' `autopilot_origin` and `autopilot_card_id`, exact RPC signatures, ownership, grants, policies and guards. Keep writes held on any mismatch, unknown transaction outcome or reload failure.

4. **Reconcile the cutover gap.** Inspect OPEN, approved, executed and auto-executed cards created or attempted during the boundary, their actual source records, trusted reminder origins and any already committed reminder receipts. Distinguish definite refusal from an unknown commit outcome. Record cards with no corresponding reminder or an inconsistent receipt. Do not infer trusted provenance from display payloads or public stamps, invent missing reminders, or retry in a way that rematerializes duplicates. Obtain an operator-reviewed disposition using the verified atomic writer and actual committed state; otherwise leave the affected work held for review.

5. **Release the exact coordinated application.** Record the approved immutable deployment commit and verify it contains the matching producer, reader, assistant recurrence, recurrence UI and database types. Replace server instances and jobs and require cached clients to reload into that release before allowing generated writes. Do not reopen the hold while any old writer or recurrence client can still act.

6. **Run production acceptance gates before resuming.** Using operator-approved accounts and synthetic records, verify a named member can read and resolve their generated reminder, an unnamed member cannot read or mutate it, another family's member cannot access it, and managers retain intended access. Confirm manual reminders still work. Reassign the actual source, refresh through the approved path and check the resulting audience. Complete and repeat a named generated reminder: verify one committed next occurrence, immutable card/family linkage, denied readers still denied, and a retry produces no duplicate. Include the real server asking-viewer path, ordinary acceptance, scheduled/on-demand writers and a reloaded recurrence client. Confirm failures return an error rather than a fabricated success. Record receipts and cleanup; resume only after every required gate and gap disposition is accepted.

Acceptance must remain bounded to the approved records. The cron GET endpoint has no family filter and may create other families' groceries or notifications, so it is not a harmless synthetic probe. Scanning does not refresh the audience of already approved/executed cards; the audience-reassignment gate needs its separately permitted card-member update. Deleting the native fixture's source means deleting its autopilot card, not the underlying insurance policy. Human create/repeat receipt retries and scan-copy behavior differ; a scan-copy timeout requires reconciliation before retry. Test partial UI outcomes and actual receipt state, not only toast text. The prepared protocol maps seven actor roles, twelve gates and seven recovery branches; no live gate has passed merely because its native analogue passed.

The broad hold blocks ordinary API writes during acceptance too. Maintenance-session role tests do not establish the ordinary API boundary. Define and independently validate a controlled acceptance mechanism before production cutover; do not silently exempt an application role or remove the hold to run these gates.

## Failure and rollback

Keep generated writes held if installation, schema-cache refresh, deployment, ownership/ACL checks or acceptance gates fail. Before a schema transaction commits, abort using the approved procedure. After it commits, an old-application rollback is incompatible with the stricter origin admission and required RPCs; it can fail writes or strand cards. Do not remove privacy guards or erase immutable origins to make an old writer work. Any post-install recovery requires a separately approved compatible application/database plan, verification of existing receipts and a repeat of the acceptance gates. Application rollback alone is not a healthy recovery path.
