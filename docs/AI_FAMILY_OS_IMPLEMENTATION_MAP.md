# Bubaly AI-First Family OS — Implementation Map

Synthesized from 12 subsystem audits (ai-core, concierge-runs, trust-permissions, notifications-activity, memory-context, proactive, domain-a, domain-b, automation, ui-surfaces, documents-search, tests-ci-security) against `SPEC.md`, plus direct verification of load-bearing facts in the repo on 2026-09-05. Revised the same day after a three-lens critique (missed assets, spec coverage, feasibility); every accepted finding was re-verified against code or SQL before folding in, rejected ones are listed in §7.

Ground truth used throughout:

- Tenant = `public.families` + `public.family_members` (role `public.member_role` parent|adult|teen|child|caregiver|guest, `lib/constants/roles.ts`; `user_id` nullable = managed profile). RLS helpers `is_family_member`, `can_manage_family` (parent|adult), `is_family_admin` (parent) in `0003_functions_triggers.sql`.
- Server tenancy = `requireUserContext()` (`lib/supabase/auth.ts`) → `ctx.active.{familyId, role, member}`; mobile Bearer path `lib/supabase/bearer.ts`. Crons use `createServiceClient()` and must scope by `family_id` explicitly.
- 265 migration files; latest `0249_model_dirty_delete_safe.sql`; **next version is 0250**. `0138` is duplicated (`0138_demo_sessions.sql`, `0138_onboarding_imports.sql`) and is renumbered only in CI by `scripts/ci-dedupe-migration-versions.mjs`.
- AI provider = OpenAI via raw `fetch` in `lib/ai/provider.ts` (no `openai` npm package; `@anthropic-ai/sdk ^0.105.0` present but used only by `lib/guardian/scam-ai.ts` and `lib/guardian/ai-screen.ts`). Key/model from `app_settings.ai_provider` then env (`lib/ai/settings.ts`). `zod ^3.23.8` installed, unused by any AI path.
- `lib/services/` contains only `descriptions.ts` / `descriptions-server.ts` (nav tooltip copy). **No general domain service layer exists**, but partial precedents do: `lib/family/actions.ts` (whitelisted, manager-gated, audited generic write path for 11 tables with an `ActionResult` contract), `lib/wallet/server.ts` ("the ONE place" money moves, over atomic RPCs from `0205`), `lib/chores/ai.ts` (degrading AI validation service), and cron+action shared cores `lib/planning/prep-server.ts runPrepGeneration`, `lib/guardian/learning-run.ts runLearningForFamily`, `lib/twin/project-server.ts runTwinProjection`, `lib/intelligence/hard-signals-server.ts runSignalDetection`.
- Scheduling = `vercel.json` (21 daily-safe Hobby crons) + `scripts/cron-dispatch.mjs` `SCHEDULES` driven by `.github/workflows/cron-dispatch.yml` every 5 min (requires repo secret `CRON_SECRET`). **Dispatcher limits** (`scripts/cron-dispatch.mjs:104-138`): each route call is aborted after 120 s, any failed route exits 1, one `concurrency: cron-dispatch` group, `timeout-minutes: 10`; `tests/cron-dispatch.test.ts:45-51` pins the list of routes whose real cadence lives only in the dispatcher. Route `maxDuration` = 60 on `/api/ai` and most crons, 300 on `/api/cron/marketing`, `/api/cron/marketing-providers`, `/api/cron/provider-sync`. Only `next/server after()` usage: `lib/reasoning/auto-refresh.ts` (a tiny best-effort twin projection).
- Standing rule (`docs/AGENT_HANDOFF.md` line 16): do NOT modify the global left navigation for all accounts without explicit instruction.
- Coordination ledgers already exist: `docs/agents/DECISIONS.md` (records "FOR-ALL write-RLS on sensitive ledgers → manager/service-role, keeping child request-row INSERT exception"), `docs/SUPABASE_WIRING_MATRIX.md` (per-domain wiring status incl. `family_ai_recommendations`, `family_automation_rules/runs`), `docs/audit/COORDINATION.md`. New AI tables must be added to the wiring matrix as part of P1-01.
- Families are created by three paths — `lib/server/ensure-family.ts`, `app/(app)/admin/actions.ts:99`, `lib/demo/session.ts:82` — and all fire the `handle_new_family()` AFTER INSERT trigger (`0003_functions_triggers.sql:67-84`), which is therefore the only place to seed per-family defaults.
- Feature gating today: `lib/constants/feature-catalog.ts` lists `ai-assistant`/`ai-concierge` as `basic` and `command-center` as `plus`; `lib/constants/plans.ts:72` marks `/dashboard/assistant` level 0 ("metered AI"); neither `app/(app)/dashboard/assistant/page.tsx` nor `concierge/page.tsx` calls `requireFeature`, and `AI_MONTHLY_ALLOWANCE` does not exist (only the "10 AI requests/month" marketing string at `plans.ts:149`).

Status vocabulary in this document: **exists** (works as specified), **partial** (works but incomplete), **mock** (present but unwired/no-op/demo data), **missing**.

## 2. Entity mapping (spec §3 → repo)

Rule: never duplicate an existing table; extend where a table already solves the problem. New tables are family-scoped, RLS via `public.is_family_member(family_id)` for SELECT and `public.can_manage_family(family_id)` where noted, every FK `on delete cascade` to `families`, `updated_at` trigger via `set_updated_at()`, all in new migrations starting at **0250**. **Write-side rule for AI ledgers** (follows `docs/agents/DECISIONS.md` and the 0217/0218/0220/0237 precedents): tables the executor writes (`ai_plans`, `ai_plan_steps`, `ai_run_events`, `ai_tool_calls`, run bookkeeping columns) get **no authenticated INSERT/UPDATE/DELETE policy at all** — SELECT only for members; every write goes through `createServiceClient()` in server code scoped by `family_id`. This closes step injection (a member inserting a `finances.updateBudget` step into a parent's run) and audit forgery (fake `run_completed`/tool-call rows feeding "Completed by Bubaly" and time-saved). Migration hygiene: enum `ADD VALUE` lives in its own migration **file** (Supabase applies each file as one transaction; see `0011_public_stats.sql:9-18`, `0095_wallet_transfers.sql:8-11`), new CHECKs on legacy free-text columns are added `NOT VALID` then `VALIDATE CONSTRAINT` after a documented `select distinct status` sanity update (header like `0237`).

## 4. Foundation design (Phases 1–3 of §62)

### 4.1 Domain service layer — `lib/services/<domain>/index.ts`

Contract shared by UI server actions, AI tools, crons:

```ts
// lib/services/types.ts (new)
export type ServiceScope = {
  db: SupabaseClient<Database>;          // caller RLS client, or service client from cron (family-scoped by construction)
  familyId: string;
  userId: string | null;                 // null for cron/system
  memberId: string | null;               // family_members.id (resolved once via family_members.user_id)
  role: MemberRole | 'system';
  actorKind: 'member' | 'ai' | 'system';
  runId?: string; stepId?: string;        // set by executor for audit/idempotency
  idempotencyKey?: string;
};
export type ServiceResult<T> = { ok: true; data: T } | { ok: false; error: string; code?: string };
```

Every service function: `fn(scope: ServiceScope, input: ZodInferred): Promise<ServiceResult<T>>`, filters `family_id = scope.familyId` explicitly (never relies on RLS alone — crons use service client), validates input with a zod schema exported from `lib/services/<domain>/schemas.ts`, records activity via `lib/services/activity` for writes, and honours `scope.idempotencyKey` through `lib/services/idempotency.ts` (reserve row in `ai_tool_calls` before write; return prior `resource_id` on conflict).

Edit flow writes `edited_payload`, status `modified`, new plan version.
- Policy/grant/delegation/dial mutations write `trust_audit_logs` rows with the new decision values.
