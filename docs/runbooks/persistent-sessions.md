# Persistent sessions

Users should remain signed in across navigation, browser/app restarts, and temporary network or storage failures. Explicit local sign-out, a revoked refresh token, or another definitive authentication rejection must still end that session. An outage must not grant access to protected data or be represented as a signed-out account.

## Application behavior

- Browser and server clients use the same persistent cookie scope and automatic token refresh. Session cookies retain the existing 400-day browser maximum; access-token expiry is not extended.
- The shared fetch boundary classifies HTTP 408, 429 and 5xx responses as retryable only for a POST to the configured project's refresh-token endpoint. This happens before the installed SDK can remove saved credentials. Password grants, logout, other hosts and definitive token rejections retain their original responses.
- Middleware preserves refreshed cookies on both the current server request and browser response, including the SDK's cache-prevention headers on redirects. Required account reads fail as unavailable during a temporary auth failure.
- The authenticated web layout reconciles its rendered identity with a successful stored-session read after foreground, online and native-resume events. Failed or stale reads cannot override newer auth events.
- All six web sign-out controls capture the intended session when opened. They clear that session locally before requesting token-specific revocation, and refuse to clear an account that changed while the control was open. A delayed provider response never repeats local cleanup or redirects a newer login.
- The ordinary browser cookie adapter fences old renewal writes and deletion against a token-free logout generation. Same-tab and cross-tab notifications request a fresh storage read; stale null receipts cannot retire a replacement account's cache. The browser SDK uses its public process lock so overlapping renewal calls settle after interrupted cleanup.
- A pre-hydration `POST /auth/signout` writes only a short-lived intent receipt, then redirects to `/auth/signout/complete`. JavaScript compares the intended session before local deletion. Missing, expired or changed intent requires a fresh explicit decision. Both logout routes skip middleware refresh, so the logout response cannot overwrite a newer login's authentication cookies.
- Password login uses an isolated operation that captures current browser ownership before waiting on the provider. It cannot replace an account saved by a newer login, consume another operation's PKCE verifier, or publish after timeout/unmount. A session is accepted only after coherent provider/JWT checks and successful persistent-cookie readback.
- Child PIN login verifies credentials on the server and returns only the authorized token pair. Browser adoption verifies that pair and remains bound to the submitted user/session. Its exact Server Action POST avoids ambient middleware cookie writes. Both login forms require a current session before navigation.
- Mobile secure storage writes a new chunk generation before committing its header. Reads support legacy sessions. Interrupted writes retain the previously committed session; cleanup failures do not invalidate a successful write. Explicit sign-out removes the readable header first. Storage failures carry a retryable error instead of becoming an absent session.
- Mobile retries unavailable bootstrap reads every 30 seconds and on foreground, including when the saved access token has not expired. Newer auth events and disposal take precedence over a pending read.
- The reconnecting screen and Settings provide explicit device sign-out with visible retry feedback. The app first requests the SDK's local sign-out. Only a retryable network or storage failure permits conditional removal of the committed secure-storage header, followed by normal SDK sign-out against the empty store. A failed deletion leaves auth state intact and shows an error; the app does not manufacture a successful sign-out event. The explicit storage key matches the SDK's existing default, so installed sessions remain discoverable.
- During that fallback transaction, writes to the auth-session key return an SDK-recognized retryable failure. They are not queued for later replay: a delayed old refresh must not overwrite a newer login. A sign-in that overlaps this brief transaction receives translated retry guidance and cannot report success without saving its session. New write attempts are accepted after success or failure. A newer session save admitted before the fallback starts invalidates its storage write revision; a condition checked inside the deletion queue then cancels fallback deletion.

## Verification and limits

The root runtime suites cover the installed AuthClient and browser/server SDKs with synthetic sessions and controlled transport failures, plus actual middleware and component lifecycle callbacks. Secure-storage tests cover interruption before and after the header commit, legacy migration, Unicode byte bounds, cleanup failure, concurrent refresh/read/sign-out and recovery after storage unlock. Explicit sign-out tests exercise corrupt storage, failed deletion, unavailable logout/refresh, overlapping password login, delayed old refresh, and successful sign-in after the transaction. Screen and provider tests verify visible errors and translated retry guidance without exposing native diagnostics. These are controlled tests, not a production Supabase or real-device session test.

Production session configuration has not been inspected. This task has no usable authenticated management connection or verified linked project. A read-only capability check on 2026-09-12 found no callable management/browser tool, management-token environment variable or local project link. The installed CLI's project listing failed with a transport error; that does not establish whether cached CLI credentials exist. Before release, verify that the project's session timebox, inactivity timeout and single-session restriction match the indefinite-session requirement. Supabase defaults to indefinite sessions, but hosted overrides can terminate them on refresh. See [Supabase session configuration](https://supabase.com/docs/guides/auth/sessions).

For the requested policy, the production project's Auth session settings should have **Time-box user sessions disabled**, **Inactivity timeout disabled**, and **Single session per user disabled**. Keep normal JWT expiry and refresh-token reuse protection enabled; extending access-token lifetime is not how the application preserves a login. These are Supabase settings, not Vercel environment variables. The documentation was checked on 2026-09-12; the actual production values still require verification.

The native SDK's implicit initial subscription previously produced an unhandled rejection if the Keychain read itself rejected. A tracked install-time correction now moves its existing initial-session error handler around that read. Both shipped runtime formats are tested with real SupabaseClient instances under strict unhandled-rejection handling; explicit getSession errors remain visible and credentials survive recovery. The patch verifies the exact locked SDK version and file hashes, fails on unknown contents, and runs through mobile installation and CI. SDK upgrades require an explicit review of this correction; see [patch maintenance and tests](../../mobile/scripts/auth-storage-errors.md). Physical-device cold-start acceptance remains outstanding.

Each test creates a unique confirmed account, household, parent membership and completed-onboarding preferences through the local Auth/REST APIs, and cleans only its own IDs. It never uses the authenticated journey's account. Remote providers are refused even when the generic remote-E2E override is set; application and provider origins must be HTTP loopback. Local reproduction uses the same disposable backend credentials and `NEXT_PUBLIC_SITE_URL=http://localhost:3107`, without `E2E_AUTH_EMAIL` or `E2E_AUTH_PASSWORD`.

The browser signs in through the real form. Coverage includes persistent cookies restored into a fresh browser context with no local storage, real GoTrue refresh after the stored SDK expiry is moved into the past, parallel middleware requests pinned to the same expired cookie, a further refresh proving the resulting session remains usable, and explicit same-origin local sign-out while a second device remains signed in. The expiry test preserves the signed JWT: it accelerates the stored-expiry condition rather than waiting for an hour or changing the provider's token policy. Only boolean comparisons reach assertions; tokens, passwords and cookie state remain in memory. Traces, screenshots and video are disabled for this spec, login pages close before context cleanup, and its failure artifacts are excluded from upload.
